# Polish — 修辞动作润色路由（唯一入口）

**执行协议（唯一权威）**：`story-blueprints/v4/rhetoric-moves/_polish-protocol.md`——六步工作流：识别动作 → 取蓝图+信号词（允许多源）→ 保内容升执行（Pollock 五病灶扫描）→ 生成变体 ×3（A 单蓝图重排 / B 跨源合成 / C 换主宾视角）→ 流畅性门八查 → 输出。本文件只路由，不重复协议内容。

## 路由规则

1. **默认**：按协议完整执行。识别动作读 `story-blueprints/v4/rhetoric-moves/_index.md` 动作分类表，**按草稿的修辞功能自动匹配**（双向预测先行/双链汇一/调节元框架/反向证伪/嵌入型补充分析/条件支付收束），用户无需点名动作；无法归类的草稿只做微观打磨，并向用户说明"这段没有明显的修辞动作，只做了微观打磨"。
2. **主诉是去 AI 腔**（"这段太像 AI 写的"）：走 `humanizer` skill；协议 §AI 腔速查表（13 型）与误报护栏同样适用。
3. **在 write-introduction/theory/methods/results 会话内**：不进本 skill——各 skill 的渲染与措辞阶段已内建润色（共用纪律见 `_polish-protocol.md` §write-* 共用纪律）。独立润色请求（无论是否来自写作会话）都进本 skill。
4. **蒸馏范文 / 整篇结构写作**：分别走 distill-*-exemplar / write-*，本 skill 只处理单句/段落级润色。

## 输出要求

- 变体 ×2–3，每个标注**采用的语料来源与替换点**（来源特异性内容必须替换：专名/数字/系数/表号）。
- 流畅性门结果（哪几查通过，任一不过即作废该变体）。
- **教学性反馈**：指出草稿原来在尝试哪个修辞动作——让用户逐渐认识动作，而不是要求提前背动作名。
- 多段落、跨章节的润色分批处理，不把整个语料库倒给用户。

## 边界

- 语料语句可直接采用，仅替换来源特异性内容防串稿；唯一闸门 = 流畅性门（通顺/学术表达/句长 20–30 词）。
- specificity gate：替换后的句子能原样放进任何一篇论文 = 不合格。
- 保留用户的领域术语、数字、因果主张与限定语；绝不编造内容。
