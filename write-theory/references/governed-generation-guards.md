# Governed generation guards

Run the catalog `generation-contract` after selecting an architecture and before
drafting. These guards constrain reasoning; they do not provide prose to copy.

## Specificity without templating

For each reasoning branch, choose one focal actor, one cue or constraint, one
resulting action, and one diagnostic observation. Do not leave alternatives such
as “attention, resources, or incentives” in final prose. Render one or two
matching reference fragments to inspect how a reasoning move becomes concrete;
transfer the move, not the source paper's constructs or wording. Rewrite the
contract as continuous argument rather than exposing checklist labels.

## E: conditional and bilateral arguments

When a boundary condition qualifies or reverses an X–Y relationship, derive
each state independently:

`boundary state S as prior scope: X → actor interpretation/capacity under S → named mechanism → Y_S`,
or in branch form `X → {high S: interpretation → mechanism → Y_high; low S: interpretation → mechanism → Y_low}`.

The boundary state is a prior scope node, never a downstream node of X: no
directed edge may run from X to the boundary state in the argument graph.
Place the boundary state before the condition-specific interpretation and
mechanism, and keep the graph and the prose in the same order. Do not infer an
average X–Y relation first and append the boundary condition afterward.

The low state cannot be written as merely “not high.” Say what actors face,
which mechanism then operates, and why it yields the stated direction. If the
two states predict opposite directions, do not add an unconditional H1 unless a
separate theory warrants an average effect. If the derivation fixes the sign
in each boundary state, state signed predictions per state (the Competing form
or a per-state hypothesis pair); reserve comparative "more positive/more
negative" wording for cases where per-state net signs are not theoretically
fixed.

## D: process theory

For each stage transition, specify an actor, a transition condition, and an
observable next state. Feedback must have a recipient and a possible effect
(reinforce, redirect, or terminate); do not convert a process model into a
universal net-effect hypothesis without independent grounds.

Use a transition marker that can be observed before the final outcome. Explain
why it demonstrates movement to the next state rather than merely renaming that
state. Close the stage chain at the terminal process state named in the task or
contribution claim; if the immediate next state is only intermediate, chain
further boundary crossings with their own markers instead of relabeling the
intermediate state as the terminal outcome.

For exact stage boundaries and feedback transport, load
`corpus/subprotocols/process_transition_operators.md`. Treat it as a structural
reasoning protocol, not an evidence-bearing exemplar.

## local-only work

Local-only work diagnoses a relationship before the paper story is confirmed.
It may map alternatives and missing evidence, but it must not number hypotheses
or propositions, claim a paper-level contribution, update `paper-state.yaml`,
or write back to the corpus.

Classify disputed elements before routing: distinct construct, alternative
operationalization, theoretical mechanism, measured mediator, contextual
condition, or temporal stage. Name at least one observation capable of
discriminating the live alternatives.
